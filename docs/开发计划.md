## 一、决策记录

这一节是**已拍板的设计决定**，不要再翻案。每条都标注了它推翻的原文。

### 1.1 骨架

| 项 | 决定 | 原 GDD |
|---|---|---|
| 游戏总长 | **21 天 = 3 周 × 7 天** | 表述含糊 |
| 行动点 | **1 点 / 天，共 21 点**；投递、打工、表演课、特殊事件各占 1 点 | 无此概念 |
| 投递上限 | **4 次 / 周**（3 周共最多 12 次） | 2 次 / 周 |
| 存档 | **每周结算自动存档** | "绝对不做存档" |
| 渲染器 | **Mobile** | Forward Plus |
| 语言 | **GDScript** | 配了 dotnet |

> 行动点是全局最硬的资源：**钱能欠，行动点只有 21 个。**

### 1.2 属性

状态栏四项：**金钱 / 演技值 / 知名度 / 风评**。另有一个**隐藏属性：负面曝光累计**（不上状态栏）。

- 「好感」系统整体砍掉（经纪人好感、朋友好感都不做）
- 「名声」统一改称**知名度**（两份 docx 已写死这个名字）
- 知名度 = 有多少观众认识你 → 决定电子报何时直接点名玩家
- 风评 = 观众对玩家的正面 / 负面评价

### 1.3 收益归属

**演技收益由角色难度决定，钱由公司档次决定。** 互不交叉。

| 角色档位 | 演技要求 | 匹配线 | 演技收益 |
|---|---|---|---|
| 龙套 | 0 | 30% | +1 |
| 配角 | 5 | 50% | +2 |
| 主角 | 15 | 70% | +5 |

### 1.4 四大 App 分工

| App | 职责 |
|---|---|
| **微信** | 消息中枢 + **投递入口**（私聊 HR）+ 经纪人提示 + 随机事件 |
| **Boss直聘** | **只读**：公司信息浏览 + HR 信息展示 + 偏好线索。玩家不在此投递 |
| **录像机** | 拼装 3 帧表情包 |
| **微博** | 每周一期电子报《有瓜有戏》 |

### 1.5 核心循环（最终版）

```
Boss直聘 ──浏览公司信息 / HR信息 / 偏好线索──┐
                                            │ 解锁 HR
录像机 ──拼 3 帧表情包──→ 表情包 ────────────┤
                                            ↓
微信 ──私聊 HR──→ 发送表情包 ══投递══→ 立即出：通过 / 失败
                                            │
                             ┌──────────────┘
                             ↓  本周末结算
                   ┌──────────────────────────┐
                   │ 《有瓜有戏》播出反馈       │
                   │ 高分 / 普通 / 低分         │
                   │ → 知名度 / 风评 / 负面曝光  │
                   │ 金钱 + 演技值              │
                   │ 房租 · PS5 分期 · 周总结   │
                   └──────────────────────────┘
                             ↓
                       结局判定 → 下周 / 结局
```

**关键时序规则**：
- 投递瞬间只出「通过 / 失败」，**不发钱不发演技**
- 钱、演技值、知名度、风评、负面曝光**全部在本周末结算**，与播出反馈一起
- 本周所有投递的作品，**统一在本周末播出**，汇总成一期电子报

### 1.6 表情包规则

- **一次性消耗**——每投一次就消耗掉，下次必须重新拼 → 保住"每次都要表演"的核心
- 录像机**不设可复用库存**；表情包列表只作**作品集 / 履历**展示
- 履历展示同时承担一个隐藏职责：为电子报的「标题调用条件」提供玩家过往经历标记

### 1.7 判定机制

**不用加权公式，用布尔条件 + 权重。**

```
匹配度 = Σ(命中的条件权重) / Σ(全部条件权重)
```

每个公司的条件是**布尔判断**（有没有"喜" / 有没有冲突情绪 / 帧间是否反转），
全部由数据驱动，好写、好测、好平衡。算出的百分比直接对接 30% / 50% / 70% 三条匹配线。

**难度层次来自条件在"质"上的差异，不是同一个数字变大。** 五档质变：

| 层级 | 公司 | 条件类型 | 玩家学到的表演概念 |
|---|---|---|---|
| L0 | A 烂片厂 | 最低条件（无冲突情绪） | 学会 UI：怎么拼满 3 帧 |
| L1 | B 小公司 | 单情绪命中 | 情绪是能被识别的 |
| L2 | C 商业片 | 情绪**纯度**（排除冲突情绪） | **克制** |
| L3 | D 文艺片 | 情绪**曲线形态**（递减 / 递增 / 平稳） | **表演弧线** |
| L4 | E 大厂 | **帧间反转** | **转折** |

> A 公司虽是最低档，但**必须给一条最低条件**，让它承担教学关职责。
> 否则玩家在 A 学不到任何东西，会带着错误认知去 B 然后连拒。

**配套硬需求**：条件越复杂，提示必须越多。「隐藏公式 + 只给情绪标签」的设定下，
**经纪人邮件是这个机制的必需品，不是可选叙事**——每家公司每周漏一条线索。

### 1.8 播出反馈

- 电子报名称：**《有瓜有戏》**，游戏中只显示标题
- 三档：**高分 / 普通 / 低分**
- 判定是二维的：**作品质量（公司档次）决定标题背景，玩家匹配度决定是夸还是骂**
  → 同一个匹配度既决定"能不能过"，也决定"播出后是高分还是低分"
- 标题称呼分级：龙套不点名 → 主要角色用角色定位 → 知名度够门槛才直呼玩家名
- **「黑红也是红」不做成成就系统**（GDD 边界写了"绝对不做成就"），改为一条微博标题

### 1.9 结局（按 12 次投递上限重写 · Day 1 二次修订）

| 优先级 | 结局 | 条件 |
|---|---|---|
| 1 | 影后 | 演技 ≥ 25 且 演过 E 公司主角 且 凑齐 PS5 费 |
| 2 | 文艺片女神 | 演技 ≥ 18 且 演过 D 公司主角 |
| 3 | 龙套之王 | **龙套档**成功演出 ≥ 8 且 演技 ≤ 12 |
| 4 | 烂片女王 | **A/B 公司**成功演出 ≥ 6 且 演技 ≤ 12 |
| 5 | 被解雇 | 累计失败投递 ≥ 8 且 欠债未清（金钱 < 0） |
| 6 | 平庸 | 凑齐 PS5 费但未达上述任何一条 |

> **⚠️ 约束一（数学）**：演技值单调递增，「成功演出 ≥ N」必然推出「演技 ≥ N」。
> 所以任何写成「成功 ≥ N 且 演技 ≤ M」的结局都必须有 **M > N**。
> 原文的「演出次数 ≥ 15 / ≥ 20」在 12 次上限下数学上不可达。
>
> **⚠️ 约束二（语义）**：龙套之王与烂片女王必须测**不同的东西**。
> 初稿把两者都写成「演得多 + 演技低」，只是数字不同 —— 玩家分不出区别，等于白做两个结局。
> 现在 **龙套之王 = 数量**（成功演了多少个小角色），**烂片女王 = 品质**（成功演了多少部烂片）。

## 二、系统架构

### 2.1 硬性架构约束

> **`scripts/core/` 下所有类必须是纯 `RefCounted`，继承 Node 的一律不准放进去。**
> 场景脚本只负责"读状态、画出来、把输入转成对核心的调用"。
> 这条不是洁癖，是**数值模拟器的前提**——见 2.3。

```
res://
├── addons/godot_mcp/
├── assets/
│   ├── parts/          # 表情部件 PNG（眼/嘴/眉/其他）
│   ├── ui/             # UI 切图、LOGO、App 图标
│   ├── portraits/      # 角色头像
│   ├── audio/
│   └── fonts/
├── data/               # ★ 数据驱动，策划改数值不用动代码
│   ├── companies/      # 5 家公司
│   ├── parts/          # 部件定义（情绪权重）
│   ├── conditions/     # 试镜条件
│   ├── events/         # 随机事件
│   ├── mails/          # 邮件模板
│   └── news/           # 电子报标题
├── scenes/
│   ├── main/           # 主场景、手机壳、状态栏
│   ├── apps/           # 微信 / Boss直聘 / 录像机 / 微博
│   ├── minigame/       # 录像机拼装
│   └── ui/             # 通用 UI 组件
├── scripts/
│   ├── core/           # ★ 纯逻辑，不碰场景树
│   │   ├── game_state.gd       # 全局状态
│   │   ├── audition_resolver.gd # 匹配度判定引擎
│   │   ├── economy.gd          # 收支结算
│   │   ├── week_cycle.gd       # 周流程状态机
│   │   ├── broadcast.gd        # 播出反馈 / 电子报
│   │   └── save_system.gd      # 存档
│   ├── data/           # Resource 类定义
│   └── apps/           # App 界面逻辑
└── tools/
    └── balance_sim.gd  # ★ 数值模拟器（headless 可跑）
```

### 2.2 数据驱动

部件、公司、条件、事件、邮件、新闻全部走 `.tres` Resource。
**策划改数值不改代码**——21 天工期里这点能救命，也是狗牙能独立推进文案的前提。

### 2.3 数值模拟器（提前到 Day 13）

`tools/balance_sim.gd` 用 `--headless` 跑，不依赖任何场景。

必须写**两种 agent**，它们测的是完全不同的东西：

| Agent | 测什么 |
|---|---|
| **随机 agent** | 收益分布、破产率、结局分布 |
| **贪心 agent** | **极端路线的可达性**——按"门槛刚好够 + 单位收益最高"做局部最优，验证「影后」和「龙套之王」两条路真的走得通 |

> 随机 agent **无法**证明可达性：随机乱投几乎必然摸不到演技 ≥ 25。
> 这一点必须在 Day 13 就跑起来，不能拖到 Day 19——那时发现数值不通已经来不及改了。
